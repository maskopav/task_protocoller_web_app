# Bulk participant import

How an admin can enroll many participants into a project + protocol at once
from a CSV of external IDs, instead of using the "Add Participant" form one
row at a time. Backend-only feature (`backend/`); the CSV upload can be
driven from any HTTP client, e.g. curl or Postman, until a frontend upload
button is wired up (see "Where things live").

## The endpoint

```
POST /participants/bulk-import
Authorization: Bearer <admin JWT>
Content-Type: multipart/form-data

file:        the CSV (see "Input format")
project_id:  the project to enroll participants into
protocol_id: the protocol to activate for each of them
```

Requires the same admin auth as every other route under `/participants`
(`requireAuth`, mounted in `server.js`) — any authenticated admin, not
scoped to admins assigned to that specific project (`createParticipant` and
the rest of `/participants`/`/participant-protocols` don't enforce that
scoping today either — see `getProjectFieldwork` in `projectController.js`
for the pattern if that's ever tightened).

### Input format

One column, one external ID per row:

```csv
external_id
PID-001
PID-002
PID-003
```

- A header row is optional. If the first row's first column is exactly
  `external_id` (case-insensitive), it's dropped; otherwise every row is
  treated as data.
- Only the first column is read — extra columns are ignored, so a richer
  export from another system can be pointed at this endpoint unmodified.
- Blank lines are skipped. A capped, generous 2MB file limit is enforced
  (`multer`, memory storage) — tens of thousands of rows.
- Parsing is intentionally minimal (`backend/src/utils/csvParser.js`):
  quoted values are unquoted, doubled quotes (`""`) become one `"`, but
  there's no support for embedded newlines. It's a plain list of IDs, not a
  general CSV import.

### Output format

The response body **is the result CSV** — the same request produces the
enrollment and returns proof of it, one output row per input row, in the
same order:

```csv
external_id,participant_id,unique_link,status,error
PID-001,42,https://app.example/study/#/participant/3f9a...,imported,
PID-002,,,skipped,Duplicate external_id in file
PID-003,43,https://app.example/study/#/participant/7c1e...,imported,
```

| Column | Meaning |
|---|---|
| `external_id` | As read from the input row (trimmed) |
| `participant_id` | `participants.id`, if the row was imported |
| `unique_link` | The participant's protocol access link, if imported |
| `status` | `imported` or `skipped` |
| `error` | Why the row was skipped, blank if imported |

A row is `skipped` (not a failed request) for: an empty external_id, a
duplicate external_id within the same file, or any error encountered while
processing that one row (see "Failure isolation"). The overall HTTP request
still returns `200` with the full CSV — a bad row never hides the results
for every other row. Only file-level problems (missing file, missing
`project_id`/`protocol_id`, inactive project, empty file) reject the whole
request with a JSON error body and a non-200 status, before any row is
touched.

### The unique link

`unique_link` is built the same way `authController.js`'s participant
signup flow already builds it — `${referer-or-origin}#/participant/{token}`
— using the request's own `Referer`/`Origin` header rather than a
backend-configured base URL, since the frontend's actual base path/port
isn't otherwise known to the backend. **This means the endpoint must be
called from (or with a `Referer`/`Origin` matching) the admin frontend's own
origin** — a bare `curl` from a different host will produce a link with the
wrong (or no) domain. `{token}` is `participant_protocols.access_token`, a
32-char random hex string generated by `generateAccessToken()`
(`backend/src/utils/tokenGenerator.js`).

## What happens per row

For each external ID (`bulkImportParticipants`, in
`backend/src/controllers/participantController.js`), inside its own
transaction:

1. **Find or create the participant.** `participants.external_id` is
   looked up first; a new row is only inserted if it doesn't exist yet
   (`findOrCreateParticipant`). The new row gets just `external_id` and
   `creation_source = 'admin'` — every other field (`full_name`,
   `birth_date`, etc.) is left `NULL`, same as the DB schema already allows
   for a participant created without those details.
2. **Find or (re)activate the assignment.** If this participant already has
   an assignment to the selected protocol *with a usable token*
   (`access_token IS NOT NULL`), that row is reactivated in place
   (`is_active = 1, end_date = NULL`) and its existing token is reused —
   so re-uploading the same or an overlapping CSV doesn't mint a second
   link for someone already enrolled. Otherwise a brand-new assignment is
   created via the shared `assignProtocolToParticipant` helper
   (`backend/src/utils/assignmentHelper.js`) — the same helper the single
   "Add Participant" flow (`createParticipant`) uses, so token generation,
   collision handling, and the `is_active = 1` default all behave
   identically here.

### Failure isolation

Each row's find-or-create-and-assign work runs in its own DB transaction
(`executeTransaction`), inside a per-row `try/catch`. If one row throws
(a transient DB error, an unexpected constraint violation), only that row is
recorded as `skipped`, with the error message in the `error` column and a
matching entry in the server log (`logToFile`) — the loop continues with the
next row. This mirrors `importContactEvents`
(`participantProtocolController.js`), the existing CSV-shaped bulk operation
in this codebase, which makes the same per-row judgment call rather than
failing the whole batch over one bad line.

Duplicate external IDs *within the uploaded file* are caught before any
query runs (skipped with `"Duplicate external_id in file"`) — only the
first occurrence of a given ID is processed.

## Where things live

| Concern | File |
|---|---|
| Route + file upload (multer, size limit) | `backend/src/routes/participants.js` |
| Controller (`bulkImportParticipants`) | `backend/src/controllers/participantController.js` |
| CSV input parsing | `backend/src/utils/csvParser.js` → `parseExternalIdsCsv` |
| CSV output serialization | `backend/src/utils/csvBuilder.js` → `buildCsv` (shared with other CSV exports) |
| Token generation + assignment insert | `backend/src/utils/assignmentHelper.js` → `assignProtocolToParticipant` |
| Same link-building approach for a different flow | `backend/src/controllers/authController.js` → `participantSignup` |
| Tests | `backend/src/utils/csvParser.test.js`, `backend/src/controllers/participantController.test.js` |
| Existing single-participant equivalent | `backend/src/controllers/participantController.js` → `createParticipant` |
| Existing CSV-shaped bulk operation (design precedent) | `backend/src/controllers/participantProtocolController.js` → `importContactEvents` |

No frontend upload UI exists yet — the Participants admin page is
`frontend/src/pages/ParticipantDashboardPage.jsx`, and the existing
single-participant modal is `frontend/src/components/Participants/AddParticipantModal.jsx`.
