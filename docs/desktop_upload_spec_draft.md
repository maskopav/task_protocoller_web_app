# DRAFT — Desktop app session upload (phase B)

> **Status: DRAFT / non-normative.** Both the web app and the desktop app are
> in development; the desktop app's own documentation is explicitly not
> definitive. This file collects what is known about the upload contract so
> phase B (receiving and browsing session data) can start from an agreed
> baseline instead of reverse-engineering the desktop client again. Update it
> as the desktop spec settles — nothing here is implemented yet.

## Source of the contract

The desktop app currently talks to a mock server
(`ShareAppNewDemo/tools/mock-server`), whose behavior the app already depends
on. Replacing the mock means matching it, then evolving:

- `GET /api/config/{installationId}` → the config fetch. Already replaced on
  this branch by `GET /site-config/:token` (the desktop client's base URL and
  path are constructor parameters in `KtorConfigApi`/`KtorUploadApi`).
- `POST /api/upload` → the session upload. **This is phase B.**

## Upload request (as the desktop app sends it today)

`POST` multipart/form-data with fields:

| Part | Type | Notes |
|---|---|---|
| `installationId` | text | The app's stored credential. Maps to `sites.access_token` here — the site token is the credential, exactly like the config fetch. |
| `sessionId` | text | Unique per recorded session, generated by the app. |
| `zipSha256` | text | Hex SHA-256 of the ZIP; server must verify. |
| `zip` | file | The session ZIP, **~165 MB typical** — must be streamed to disk, never buffered in memory (`multer.diskStorage` + explicit `limits.fileSize`, NOT `memoryStorage`; the global `express.json` 5 MB limit does not apply to multipart). |

## Responses (mock-server contract the app already handles)

| Status | Body | When |
|---|---|---|
| 200 | `{"status":"ok","sessionId":…,"bytes":…,"sha256":…,"receivedAt":…}` | Stored verbatim by the app in `metadata/upload_status.json`. |
| 404 | error | Unknown installation id / site token. |
| 409 | error | Session already uploaded (upload-once semantics). |
| 400 | error | Missing multipart fields or SHA-256 mismatch. Listing the part names actually received in the 400 body has proven valuable for debugging multipart issues. |

## Sketch of the web-app side (not implemented)

- New table, parented to sites (the phase-B replacement of the old
  participant sessions chain):

  ```sql
  CREATE TABLE site_sessions (
    id integer PRIMARY KEY AUTO_INCREMENT,
    site_id integer NOT NULL,            -- FK sites
    session_uid varchar(255) UNIQUE NOT NULL,  -- the app's sessionId (upload-once via UNIQUE)
    zip_path varchar(512) NOT NULL,
    zip_sha256 char(64) NOT NULL,
    zip_bytes bigint NOT NULL,
    received_at timestamp DEFAULT CURRENT_TIMESTAMP
  );
  ```

- Endpoint `POST /site-uploads` (public, credential = site token in the
  multipart body, like the mock). Streams to `DATA_PATH`, verifies the hash,
  inserts, returns the contract above.
- Admin browsing: rework the kept-but-unmounted **Fieldwork** components
  (`frontend/src/pages/ProjectFieldworkPage.jsx`,
  `frontend/src/components/Fieldwork/*`) into an upload browser: per project
  (via `site_projects`) or per site, listing session uploads with size,
  hash-match status, received time, and a download action. The backend
  currently has **no file-serving endpoint at all** — downloads are new
  surface area (auth required; recordings are sensitive clinical data).

## Open questions (blockers to resolve before implementing)

1. **Project provenance of an upload.** A site can inherit protocols from
   several projects; the upload carries only `installationId` + `sessionId`.
   Either the ZIP metadata (`examination.json` /
   `task_configuration_snapshot.json`) identifies the protocol — from which
   the project can be derived — or the contract needs an explicit
   protocol/project field. Multi-project sites make this mandatory, not
   cosmetic.
2. **`installationId` ↔ site token.** One site (token) may run several
   physical installations. If per-installation identity matters (it appears in
   `${installationId}` filename templates), the upload needs to carry both, or
   sites need child installation records.
3. **Endpoint paths.** `/api/config/{id}` and `/api/upload` are mock-server
   placeholders; the desktop repo lists the real path as an open question.
   Agree on `/site-config/:token` (already live) and `/site-uploads` before
   the desktop side hardcodes anything else.
4. **Retention/limits.** Max ZIP size (`limits.fileSize`), disk quota per
   site, and whether re-upload after a failed hash check is allowed (mock: a
   400 hash mismatch does not consume the session id; a 200 does).
